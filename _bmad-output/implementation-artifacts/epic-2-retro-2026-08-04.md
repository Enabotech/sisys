### 2.2 "可选增强注入 + 三级降级" 模式建立

**来源：** Story 2.3 首次创建，2.4/2.5/2.8 复用

```python
# 模式定型（Story 2.5 OCR 最完整版本）
class DocumentParsingService:
    def __init__(
        self,
        parser: DocumentParserPort,
        layout_detector: LayoutDetectorPort | None = None,   # Story 2.3
        table_extractor: TableExtractorPort | None = None,   # Story 2.4
        ocr: OCRPort | None = None,                           # Story 2.5
    ):
        ...

    async def parse(self, doc_id: UUID) -> ParsedDocument:
        result = await self.parser.parse(doc_id)
        # 三级降级：None→跳过 / 异常→WARNING+原始结果 / init失败→raise
        if self.layout_detector is not None:
            try:
                result = self._apply_layout(result)
            except Exception:
                logger.warning("版面检测失败，返回原始解析结果")
        ...
```

**为什么成功：**
1. 符合六边形架构：领域层 Protocol + 基础设施层实现 + 应用层可选注入
2. 优雅降级而非硬失败：OCR 不可用时文档解析仍正常工作
3. 零额外依赖：不注入增强端口 = 零开销
4. 跨 Story 复用：4 个 Story 使用同一模式，认知负荷低

## 三、挑战与痛点

### 3.1 AsyncMock 协程泄漏 RuntimeWarning（跨 Story 顽固问题）

**影响范围：** Story 2.6（版本快照 CLI 测试）+ 跨测试 GC 污染至契约测试

**根因：** `asyncio.run` 被 `unittest.mock.patch` 替换后，`AsyncMock` 方法调用产生的协程对象永远不会被 await — mock 版 `asyncio.run` 直接返回预设值。

**为什么顽固：** 此问题从 Epic 1 延续至 Epic 2。Epic 1 回顾中未将其识别为独立模式，导致 Epic 2 中重复出现（`d5d69ca3` 和 `c5b58754` 两个修复提交 + 今日第三个修复）。

**最终修复模式（2026-08-04）：**
```python
# 错误 ❌
mock_service = AsyncMock()          # 产生未 await 的协程
mock_service.method.return_value = x

# 正确 ✅
mock_service = MagicMock()          # asyncio.run 已被 patch，不需要 AsyncMock
mock_service.method.return_value = x
```

**教训：** 此模式应纳入审查反馈检查清单，防止在 Epic 3 中第三次出现。

### 3.3 Story 2.5 (OCR) 部署复杂度

Story 2.5 是 Epic 2 最复杂的 Story（1,335 行文档），主要原因：
- Docker 服务化部署：2 个容器（vLLM 推理 + API 服务）、GPU 直通、CUDA 12.9+
- 镜像大小 ~13-15GB
- 需要 RTX 5090 (Blackwell SM120) GPU
- 部署配置涉及 `docker-compose.yml` 修改 + `paddleocrvl.yaml` 参考模板 + `envparam` 环境变量

**影响：** CI/CD 环境无法运行 OCR 集成测试（无 GPU），依赖手动验证。

### 3.4 版面检测 IoU 匹配的 MVP 降级 — ✅ 已修复 (2026-08-05)

**原状（Story 2.3 Dev Notes 明确记录）：**
> `PDFParser` 不输出 bbox（所有 `ParsedElement.bbox=None`），IoU 匹配无法工作。因此采用**顺序索引匹配**作为 MVP 临时方案。当 `PDFParser` 未来输出真实坐标时，需切换为 `match_detections()` IoU 算法。

**修复（2026-08-05）：**
- PDFParser 通过 `visitor_text` 提取逐行文本位置，输出归一化 [0, 1] 页面坐标 bbox
- OnnxLayoutDetector 输出同样归一化到 [0, 1]
- `_apply_layout_detection` 主路径切换为 `_match_by_iou()` → `match_detections()` IoU 空间匹配
- 降级路径保留：visitor_text 失败时回退为顺序索引匹配

## 九、关键洞察

1. **学习经验级联是 Epic 2 最大的流程创新** — 7 级逐级传递保证了"同一个坑不踩两次"。建议将此模式固化为全项目 Story 模板，而非 Epic 2 特有。

2. **"可选增强注入 + 三级降级"应写入架构决策记录** — 这是 Epic 2 贡献的架构模式，已在 4 个 Story 中验证有效，值得在 `architecture.md` 中正式记录。

3. **技术债需要 tracking 机制** — MVP 降级项（PDFParser bbox）记录在 Dev Notes 中但无 sprint-status 跟踪，容易在跨 Epic 时被遗忘。应在 sprint-status.yaml 中为降级项建立 key。

4. **AsyncMock 问题是系统性测试模式缺陷** — 3 个 Epic（1, 2, 修复提交）中反复出现，说明需要流程层面（而非逐个修复）的解决方案。纳入审查检查清单是最低成本的预防措施。

5. **ADR 格式的决策记录降低了 Epic 3 的技术风险** — 当 Epic 3 需要理解"为什么选 pypdf 而非 pdfplumber"或"为什么 OCR 用 PaddleOCR-VL"时，Story 2.2a/2.5 的 Dev Notes 提供了完整上下文，无需重新调研。

6. **并行执行机会未被利用** — Epic 2 的 7 个 Story（2.2b-2.8）均依赖 2.2a 但互不依赖，理论上可并行。Epic 3 有类似机会（3.1b/3.4/3.9 依赖 3.1a），应主动规划并行。
