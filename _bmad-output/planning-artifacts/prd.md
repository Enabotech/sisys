## Executive Summary

### 愿景对齐

**sisys** 是面向**大中型企业高管团队**、**企业战略与市场体系人员**和**专业顾问**的 AI 驱动战略规划与决策智能平台。系统通过多 Agent 协作（CEO/CFO/CMO/CTO/COO/CHO/AUD 七种专业角色）和内置合规审计（7 年 WORM 存储），解决企业战略规划中的**核心痛点**：

**战略规划（SP）与业务执行（BP）的断裂。** 企业每年投入数月做战略规划，但 SP 做完锁进抽屉，BP 另起炉灶另搞一套——方向与执行之间横亘着一条鸿沟。sisys 的不可替代价值在于：

> **SP 把控方向与节奏，BP 落实推进业务执行。** 这是 sisys 在战略管理中不可替代的独特价值，也是企业从”规划”走向”作战”的核心枢纽。

sisys 将企业战略规划（SP）与年度业务计划（BP）深度咬合，形成 **”方向—解码—执行—反馈”** 的完整闭环：

| 价值维度 | SP（战略规划） | BP（业务计划） |
|---------|---------------|---------------|
| **核心使命** | 做正确的事：定义企业未来 3-5 年的方向、战略控制点和里程碑节奏 | 正确地做事：将 SP 转化为可衡量、可追踪的年度作战任务与资源分配 |
| **关键产出** | 市场洞察、战略意图、业务设计、创新焦点、风险全景视图 | 年度必赢之战、KPI 与目标责任书、预算与人力部署、执行里程碑 |
| **sisys 如何实现** | BLM 六阶段流程 + 多 Agent 辩论，精准锁定方向与阶段节奏 | BEM 战略解码引擎，自动将 SP 输出映射为结构化的 BP 框架与追踪指标 |
| **协同机制** | SP 为 BP 提供输入：今年的 BP 正是 SP 的第一年落地 | BP 向 SP 反馈执行数据，驱动 SP 滚动刷新，保证方向与节奏动态最优 |

**sisys 的独特优势：** 战略与执行之间不再有鸿沟。从 SP 的战略控制点识别，到 BP 的年度硬仗分解，再到执行偏差的预警与复盘，全部在统一平台内完成，确保企业方向不偏、节奏不乱、执行不落空。

其次是三个增效痛点：
1. **高管团队协调难** — 战略规划需要多角色视角，但高管时间难以协调，决策质量依赖个人经验
2. **数据分散决策难** — 决策质量依赖数据，但企业数据分散在不同系统，难以形成完整洞察
3. **流程长效率低** — 大中型企业战略规划参与人员多、流程长、效率低，从数周到数月不等

**核心价值主张：**

| 用户群体 | 核心价值 | SP→BP 闭环价值 |
|---------|---------|---------------|
| **高管用户** (CEO/CFO/CTO 等) | 通过 AI 协作在几天内达成战略共识，而非数周会议；决策质量提升 40% | SP 置信度：30 秒理解战略态势，战略管理（方向/解码/执行）一览 |
| **企业战略与市场体系人员** | 标准化战略分析流程，快速获取专业洞察，减少重复性数据整理工作 | BP 置信度：SP 控制点→BP 举措逐条映射可追溯，消除解码失真 |
| **顾问用户** | 3 小时完成原本需要 1 天的分析报告，效率提升 3 倍，输出质量标准化 | 全链条信任：白标输出 + 高保真溯源，客户因"可验证"而信任 |
| **企业用户** | 战略规划周期缩短 50%，确保战略落地执行，7 年审计追踪满足合规要求 | EM 置信度：资源约束校验 + 里程碑验证 + 偏差预警，计划可落地 |

**未来状态：** 战略不是高高在上的空中楼阁，而是快速智能响应业务动态的"军中诸葛亮"。

### What Makes This Special

**碾压性优势：**

| 能力 | 用户价值 |
|------|---------|
| SP→BP 全流程闭环 | SP 把控方向与节奏，BP 落实推进业务执行，消除规划与执行的断裂 |
| 输入企业数据 → 最优战略规划 | 精准高效制定 SP/BP，避免人为偏差 |
| 输入专业数据 → 高质量洞察报告 | 生成专业级商业洞察，支持客户交付 |
| 快速响应市场动态 | 实时提供高质量商业决策支持 |

**核心差异化：**

1. **SP↔BP 信任闭环** — 从 SP 到 BP 到执行设计的完整链路，战略管理（方向/解码/执行）可视化，SP 掌控方向与节奏，BP 保障落地推进。内置 BLM/BEM 模型保证 SP→BP 映射可追溯，决策舱内通过解码追溯带（Decode Ribbon）一键跳转 SP 控制点↔BP 举措
2. **多 Agent 协作** — 模拟高管团队的多视角辩论，通过红蓝对抗机制输出风险全景视图，辩论共识度实时可视化（强共识/弱共识/分歧）
3. **三重置信度评分系统** — SP（方向分）/BP（解码分）/EM（执行分）三重独立评分，物理仿真动画（流光→光晕/震动→平滑计数→呼吸态），最弱维度自动高亮提示
4. **数据驱动决策** — RAG+ 知识图谱确保决策基于事实，支持高保真视觉级溯源（Bounding Box 跳转至原始文档坐标点）
5. **合规内建** — 7 年 WORM 存储、审计追踪、数据主权隔离，满足 SOX/ISO27001 合规要求
6. **三页面驾驶舱** — 决策舱（战略推演 + 实时 AI 代偿）、工作台（七层证据树 + 辩论追溯）、战略地图（BSC 四层瀑布流：财务→客户→内部运营→学习与成长，含因果箭头与折叠展开交互）
7. **物理仿真交互模型** — 自定义滑块支持惯性动量、notch 吸附、涟漪反馈、弹簧回弹；评分条支持流光扫过→颜色过渡→数字平滑计数→持续微呼吸四阶段动画交响乐
8. **AI 代偿引擎** — 实时检测参数风险梯度，自动生成多策略排序建议（含预测影响量化 + 采纳/预览/撤销操作），叙述性风险解释（"你调整了什么→这意味着什么→安全边际还有多少"）

**核心洞察：**
- 战略管理的最大失败不是"没有规划"，而是**规划与执行之间的断裂**——SP 做完锁进抽屉，BP 另搞一套
- 战略规划的本质是**多视角共识构建**，而非单点分析优化
- 战略执行的关键是**闭环追踪与可验证**，而非规划文档本身

**开发模式详细说明：**

本项目采用**SDD+TDD 融合开发模式**，将规范驱动（SDD）与测试驱动（TDD）有机结合，通过 AI Code Agent 智能辅助，实现质量内建：

1. **SDD 规范驱动** - 保证方向正确
   - 领域事件 Schema 定义（Pydantic V2）
   - API 契约定义（OpenAPI 3.1）
   - 验收标准定义（Gherkin 格式/pytest-bdd）
   - 数据模型定义（SQLAlchemy）

2. **TDD 测试驱动** - 保证实现正确
   - 红阶段：在实现之前编写失败测试
   - 绿阶段：编写刚好让测试通过的最小实现
   - 重构阶段：保持测试通过的前提下优化代码

3. **AI Code Agent 智能辅助** - 提升开发效率
   - 生成测试初稿
   - 辅助实现代码
   - 提供重构建议
   - 规范验证

- 整体覆盖率 ≥80%
- 严重错误 = 0，高危漏洞 = 0

### Technical Architecture Considerations

#### 多租户架构设计

**混合隔离策略：**

```
┌─────────────────────────────────────────────────────────────┐
│                    应用层 (多租户感知)                        │
│  ┌─────────────────────────────────────────────────────┐    │
│  │             租户解析中间件                           │    │
│  │    (从 JWT/域名/请求头提取 TenantID)                   │    │
│  └─────────────────────┬───────────────────────────────┘    │
│                        │                                     │
│  ┌─────────────────────▼───────────────────────────────┐    │
│  │              数据隔离层                               │    │
│  │  ┌─────────────┬─────────────┬─────────────┐         │    │
│  │  │ Schema 隔离  │ 行级隔离     │ 对象存储隔离 │         │    │
│  │  │ (企业租户)   │ (顾问租户)   │ (项目数据)   │         │    │
│  │  └──────────────┴─────────────┴─────────────┘         │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

**隔离策略详解：**

| 租户类型 | 隔离级别 | 实现方式 | 适用客户 |
|---------|---------|---------|---------|
| **企业租户** | Schema 级隔离 | PostgreSQL Schema per Tenant | 大型企业、中型企业 |
| **顾问租户** | 行级隔离 | Row-Level Security + TenantID | 小型咨询公司、个人顾问 |
| **项目级隔离** | 对象存储隔离 | MinIO Bucket per Project | 所有客户 |

**技术实现要点：**

| 组件 | 技术选择 | 隔离机制 |
|------|---------|---------|
| **数据库** | PostgreSQL 15+ | Schema 隔离 + RLS (Row-Level Security) |
| **向量库** | Qdrant 1.7+ | Collection per Tenant |
| **缓存** | Redis 7.0+ | Key 前缀隔离 (tenant:{id}:...) |
| **对象存储** | MinIO | Bucket per Project + 策略隔离 |
| **消息队列** | RabbitMQ | VHost per Tenant |

#### API 设计规范

**API 设计原则：**

- **RESTful 风格** - 资源导向、HTTP 动词、状态码
- **OpenAPI 3.1 规范** - 自动生成文档、SDK、Mock 服务
- **版本管理** - URL 路径版本化（/api/v1/...）
- **认证授权** - OAuth 2.1 + JWT
- **速率限制** - 令牌桶算法、分层限流

**API 端点示例：**


### 1. 文档与数据管理（DM - Document & Data Management）[or.md 二.1-二.2]

**P0 (MVP) - 8 项：** 文档上传解析基础能力，支持高保真溯源和文档版本管理

- **FR-DM-01 (P0):** 用户可以上传 17 种格式的文档（pdf/txt/doc/docx/ppt/pptx/xls/xlsx/csv/jpeg/png/gif/markdown/html + zip/tar 压缩包）[or.md 二.1.(1)]
- **FR-DM-02 (P0):** 系统可以解析上传文档并提取文本、表格、图像、公式内容 [or.md 二.1.(2)]
- **FR-DM-03 (P0):** 系统可以保留文档版面信息（元素坐标 x, y, width, height），采用 DocLayNet 标准格式 [or.md 二.1.(2)]
- **FR-DM-04 (P0):** 系统可以提取表格的行列语义，输出包含表头与列类型的结构化 JSON [or.md 二.1.(2)]
- **FR-DM-05 (P0):** 系统可以对扫描件或图像 PDF 进行 OCR 解析（中/英），提取置信度并标注 [or.md 二.1.(3)]

| Tier | 数量 | 参数示例 | 说明 |
|------|------|---------|------|
| **环境** | 4 | mkt_growth（市场增速%）、localization（国产替代率%）、policy_support（政策支持度）、comp_lead（竞品提前月数） | 外部宏观/竞争环境参数 |

| **执行** | 10 | rd_budget（研发预算¥亿）、sales_cost（销售费用¥亿）、supply_cost（供应链成本¥亿）、hc_gap（人才缺口人）、salary_comp（薪资竞争力%）、talent_pool（人才市场热度分）、train_cycle（培养周期月）、launch_cycle（产品上市周期月）、budget_measure_match（预算-措施匹配度%）、owner_accountability（责任人明确度%） | BP 落地执行参数 |

### 11. 接口与协议（IF - Interface & Protocol）[interface-design.md v2.1]

**P0 (MVP) - 4 项：** CLI 七原则合规、Skills 三级加载、SAP 协议 Schema 定义、事件监听基础

- **FR-IF-01 (P0):** 系统可以保证 CLI 接口符合七条核心原则（P1-P7）[interface-design.md 1.2]
  - P1: CLI 是 LLM 的母语 — 内部工具 100% 有 CLI 入口
  - P2: Skills = 渐进式披露 — Agent 启动上下文 < 500 tokens
  - P3: Skill = SOP — 23 种工具各有完整 SOP（操作流程/失败处理/兜底策略）
  - P4: MCP 退居生态层 — MVP 阶段 MCP 代码量 = 0
  - P5: Less scaffolding — 工具选择准确率 ≥ 85%，避免硬编码分类器
  - P6: 负向触发条件 — 误触发率 < 5%，明确"何时不应触发"
  - P7: input_examples 驱动 — 复杂工具提供 1-5 个典型输入示例，工具调用准确率 ≥ 90%
  - **验收标准：** CLI 命令覆盖 6 个服务模块（document/tool/agent/plan/checkpoint/archive），所有命令支持 `--yes`/`--dry-run`/`--mock` Agent 参数
- **FR-IF-02 (P0):** 系统可以执行 Skills 三级渐进式加载（L1 元数据→L2 SOP→L3 资源）[interface-design.md 4]
  - L1: TOOLS.md (< 200 tokens) — 工具元数据清单，Agent 启动时加载
  - L2: SKILL.md (< 500 行) — SOP 完整定义，任务匹配后加载
  - L3: scripts/references — 按需加载资源（Python 脚本/理论参考/模板）
  - **验收标准：** Agent 启动上下文 < 500 tokens，SkillSelector 推荐准确率 ≥ 85%（关键词 40% + 语义 60% 融合排序）
- **FR-IF-03 (P0):** 系统可以定义 SAP（sisys Agent Protocol）消息 Schema，支持 Agent 间辩论/裁决/公共黑板 [interface-design.md 6]
  - 消息类型：REQUEST/RESPONSE/NOTIFICATION/BROADCAST/DEBATE
  - 消息优先级：LOW/NORMAL/HIGH/URGENT
  - 公共黑板：支持 MVCC（多版本并发控制），中间结论附带置信度与引用源
  - **验收标准：** SAPMessage Pydantic 模型定义完成，包含 message_id/conversation_id/sender_id/receiver_id/message_type/priority/content/correlation_id/isolation_level/blackboard_visible 字段
- **FR-IF-04 (P0):** 系统可以监听 10 种领域事件并触发下游用例，保证事件处理幂等性 [interface-design.md 12]
  - 监听事件：DocumentProcessed/ToolExecuted/AgentDecided/CheckpointReached/CorrectionApproved/StrategicDeviationWarning/HeartbeatTriggered/IsolationLevelSwitched/CheckpointRecovered/RoutingDecided
  - 幂等性保证：基于 event_id 的 Redis 缓存检查（TTL 7 天），支持事件重放与失败重试
  - 双通道分发：Redis Pub/Sub（实时通知）+ RabbitMQ（持久化）
  - **验收标准：** 事件处理成功率 ≥ 99%，幂等性检查准确率 100%，失败自动重试（最多 3 次）

## Non-Functional Requirements

### 概述

**非功能需求（NFR）定义：**
NFR 定义系统**表现得多好**，而不是它**必须做什么**。它们指定质量属性，如性能、安全性、可扩展性等。

**选择性方法：**
我们只记录对 **sisys** 重要的 NFR。如果某个类别不适用，我们完全跳过它。

**NFR 与 FR 的关系：**
- **FR（功能需求）** 定义 WHAT（系统必须做什么）
- **NFR（非功能需求）** 定义 HOW WELL（系统必须做得多好）
- **算法细节**（如 RRF 参数、UDMR 评分公式）在 NFR 中定义，FR 引用

**NFR 优先级：**
- **P0（MVP 必需）** - 性能/安全性/合规性/可靠性，MVP 必须通过验收测试
- **P1（V1 增加）** - 可扩展性/集成性/可访问性，V1 必须满足
